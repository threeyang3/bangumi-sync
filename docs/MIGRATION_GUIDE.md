# 路径模型升级与迁移指南

## 升级前

建议先备份 Obsidian Vault。本次升级不会自动删除 Markdown，也不会强制重命名已有文件。

## 首次扫描

插件会按 frontmatter ID 建立本地双向注册表。旧 `BangumiID` 仍兼容；ID 缺失、同一 ID 出现在多个文件或多个身份来源不一致时会进入诊断报告，危险写操作被阻止。

没有旧 `lastManagedPath` 的文件按保守策略保护。6.10.1 仅在旧文件的当前路径正好等于本次碰撞候选的当前模板首选路径时推断为插件管理；自定义文件名继续保留，也不会为无关文件逐个请求 API。

## 推荐流程

1. 运行“检查本地 Bangumi 条目”。
2. 导出诊断报告并处理 `blocking-error`。
3. 运行“预览并应用当前路径模板”。
4. 默认只迁移明确标记为 `managed` 的路径。
5. 如确认旧文件确由插件管理，可在预览中显式包含“状态未知”的旧路径。
6. 只有在确认预览后点击“应用迁移”。

用户重命名路径默认不参与迁移；必须显式勾选才会进入计划。迁移会再次验证源文件、目标占用和 ID 所有者，并通过事务执行。

## 同名条目

如果两个插件管理条目会得到同一规范化首选路径，年份互异时使用 `名称（年份）.md`；同年或缺年时追加 `[bgm-ID]`。全角斜杠是文件名字符，不是目录边界；升级后 `乱马1／2.md` 不会与 `乱马1/2.md` 误判为同一路径。

同步先生成内容，再提交碰撞组重命名与写入。若内容生成失败，旧文件不会移动；若重命名后的写入失败，插件会自动恢复新建文件、原内容和原路径。出现 `rollback-failed` 时应停止后续写入、检查诊断报告和 Vault 回收站，再手动核对相关 ID。

## 模板变化

普通同步不会因为模板变化批量移动文件。模板只用于新条目；现有文件迁移必须走预览功能。相关条目链接通过注册表的当前路径生成，Obsidian 重命名 API负责保持 Vault 链接一致。

## 升级到 6.10.2

从 6.10.0 或 6.10.1 升级不需要路径迁移。同步部分成功时，请先在结果窗口选择保留或回滚，再开始下一批。“保留成功结果”先保存当前 ID/路径注册表；“回滚本批次”恢复新建文件、覆盖前内容、重命名前路径和批次前注册表快照。

出现 `rollback-failed` 后，不要继续批量重命名；应先核对诊断详情及 `.bangumi-sync-*.tmp.md` 文件。

## 升级到 6.10.3

无需迁移现有笔记或 `subjectPathStates`。未决批次的按钮现在是原子操作，回滚后的统计表示最终磁盘状态。

若出现 `rollback-failed`，插件会暂停所有新同步和路径迁移并保留恢复上下文。优先重试恢复；如已手工恢复，请先清理 `.bangumi-sync-*.tmp.md`、重复 ID 与身份冲突，再执行人工恢复确认。只有本地重扫与一致性检查无阻塞项后才能继续同步。

## 升级到 6.10.4

无需迁移现有笔记或设置。rollback-failed 后可从命令面板重新打开 Recovery Center。人工处理时，按诊断恢复：删除本应不存在的 unexpected 文件；补回 missing 文件；把路径恢复为批次前路径；若期望路径属于其他 ID，先修正文件身份或移走错误文件。确认动作会重新保存原 `subjectPathStates`、比较内存状态并二次扫描，全程不访问网络。

恢复上下文存在期间，所有用户可触发 Vault/插件状态写入均被阻止；只读诊断与恢复扫描可用。Retry 与 Manual Confirm 不能并行。请不要依赖重启来恢复 6.10.4 的内存上下文；持久化事务日志和重启自动恢复仍在 Issue #5。
