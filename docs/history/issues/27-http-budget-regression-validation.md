# Issue #27：正式执行的 HTTP 预算回归

## 问题与修复

用户反馈 6.13.0 正式执行由 464 秒增加至 578 秒，其中资料准备与路径规划由 123 秒增加至 274 秒。不能用预览阶段的加速抵消这一回归，也不能把减少请求次数当作完整执行提速的证据。

6.13.0 将条目并发设置直接用于共享 HTTP 上限。旧版一个条目可同时请求 subject、characters、persons、relations，五个条目最多产生二十个资料请求；6.13.0 将总请求限制为五个。预览会话保留的临时预算也会影响正式执行，因此必须同时调整设置应用、全部同步入口和预览会话。

修复采用兼容旧版资料扇出的预算：HTTP 上限为条目并发乘四（最多二十，默认十二）。这是兼容策略，不是 Bangumi 官方推荐速率或经过线上调优的最佳值。预览详情 worker 仍限制为原来的条目并发，文件处理并发不变；按需加载、缓存、统一请求调度、重试和取消继续生效。

## 固定延迟回归测试

`tests/api/requestThroughput.test.ts` 使用真实客户端、共享调度器与真实预览会话，替换网络传输为每次 100ms 的确定性响应。每组五个条目 worker、五十个条目。

| 场景 | HTTP 上限 5 | 上限 10 | 上限 15 | 上限 20 | 请求次数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 已缓存 subject，三类关联资料 | 3000ms | 1500ms | 1000ms | 1000ms | 150 |
| 已缓存 subject，仅关联条目 | 1000ms | 1000ms | 1000ms | 1000ms | 50 |
| 未缓存 subject，三类关联资料 | 4000ms | 未测 | 未测 | 2000ms | 200 |

断言同时覆盖条目身份、请求总数、实际峰值和在途请求归零。预览会话始终存活，避免遗漏其临时预算对执行的影响。单独测试过大预算仍被限制为二十个实际请求。

## Production Obsidian Sandbox

在隔离 Vault 中加载已经发布且下载校验过的 6.13.0 bundle 与修改版 production bundle，按旧、新、新、旧顺序比较，避免把执行顺序当作收益。每次运行使用独立输出目录、相同五十个合成动画条目、并发五、无预览缓存、关闭封面下载。HTTP fixture 每次响应延迟 100ms。

- 丰富模板读取角色、声优、制作公司、章节与观看状态，并开启关联链接；每轮 300 个请求。
- 简单模板只读取完整 summary，关闭关联链接；每轮 50 个请求。
- 每轮必须成功创建五十份文件；逐份核对完整 summary，丰富模板额外核对角色、制作公司和已看章节。

| 场景 | 6.13.0 两轮正式同步 | 修改版两轮正式同步 | 均值变化 |
| --- | --- | --- | --- |
| 丰富模板 | 7726.6 / 7591.6ms | 7097.2 / 6967.5ms | 7659.1 → 7032.4ms，减少约 8.2% |
| 简单模板 | 2148.5 / 2140.7ms | 2123.2 / 2152.4ms | 2144.6 → 2137.8ms，基本持平 |

八轮共四百份文件通过内容检查；全部结束时 manager idle、无待恢复 journal、无控制台错误或异常。丰富模板实际 HTTP 峰值由五增至六，简单模板仍为五。该本地 HTTP 传输实际只达到六并发，不能用本组结果预测真实 Bangumi 服务的吞吐，也不能将调度单测的倍数作为端到端加速倍数。

另外在修改版真实运行时验证：条目并发一应用为 HTTP 预算四；保存并发五的设置注入失败后仍维持预算四；还原设置保留同一空闲 manager。取消后排队请求不发送、旧取消上下文不复活、独立后台请求不被错误取消、预览超时跳过排队请求。429 和首次 500 两次请求后成功，401 一次失败，持续 500 四次后失败；退避期间取消不会继续请求。没有输出凭据或用户正文。

本地门禁：Node 22，npm ci、lint、397 项测试（47 个文件）、production build、docs:check、git diff --check 通过。

## 尚未验证

没有使用用户真实账号重跑 1303 条目，也没有完整复测 6.12.2。因此不能断言 578 秒已恢复到 464 秒或更低。未缓存详情时，按需加载仍需要先获取完整 subject 才能决定关联资料需求；这部分依赖关系没有被本次预算修复消除。请求预算增加也不保证远端不会限流，仍依赖现有有界重试。

本次修改未发布，不据此回复或关闭 issue。后续真实同配置复测应分别记录预览、资料准备、章节渲染、写入和正式执行总耗时，避免再次混淆不同阶段的性能。
