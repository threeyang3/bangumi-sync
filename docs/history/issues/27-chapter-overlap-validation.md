# Issue #27：章节请求与关联资料重叠加载

## 对照边界

本轮基线为已完成 HTTP 预算修复的本地提交 c69809d，不是发布版 6.13.0。两版使用相同的条目并发五、HTTP 预算二十，仅比较提前加载章节的增量收益。

在相同隔离 Obsidian Sandbox 中，按基线、修改版、修改版、基线顺序执行。每版每轮各同步五十个丰富模板动画条目和五十个简单模板条目，每次使用新的输出目录；本地 HTTP fixture 每次响应延迟 100ms。丰富模板开启关联链接，包含角色、制作公司和章节；简单模板关闭关联链接，仅使用 summary。关闭封面下载，不复用预览缓存。

## 阶段测量

使用同步入口的 onPhaseProgress 回调累计阶段墙钟时间，不加入产品日志，也不记录请求凭据或正文。以下为两轮均值，单位毫秒：

| 丰富模板阶段 | 基线 | 章节重叠加载 |
| --- | ---: | ---: |
| 资料准备 | 3701.5 | 5599.1 |
| 生成内容 | 2190.2 | 2.5 |
| 文件写入（包括事务持久化） | 1099.1 | 1090.0 |
| 正式执行总计 | 7008.4 | 6716.0 |

丰富模板完整同步减少约 4.2%。章节等待大部分转移到资料准备，不能把生成内容阶段减少约两秒宣称为总耗时减少两秒。实际单轮总耗时：基线 7086.9 / 6929.9ms，修改版 6885.2 / 6546.8ms。

简单模板：基线 2275.0 / 2113.5ms，修改版 2125.8 / 2137.9ms。没有增加请求，差异包含文件写入波动，不视为明确加速结论。

丰富模板每轮仍为 300 个请求，简单模板每轮 50 个请求。实际 HTTP 峰值分别为六和五。八轮共四百份文件逐份检查，完整 summary、角色、制作公司、已看章节均保留；结束时 manager idle，无遗留 recovery journal，无控制台错误或异常。

本轮没有独立测量 SDK 内部连接等待、插件调度队列和网络响应各自的时间，也没有拆分文件写入中的 journal 占比。阶段证据支持“此前生成内容阶段主要等待章节”，不支持精确归因全部网络成本。此本地传输最高只达到六并发；不能据此预测真实 Bangumi 服务和用户 1303 条目的耗时。

## 实现与安全检查

完整 subject 返回并确定模板需求后，章节/用户状态链与关联资料并行；同一 worker 等待二者结束再领取下一个条目。只在本批次准备结果保存章节，不做跨同步缓存，不提前修改 Vault。空章节仍跳过用户状态；章节错误降级结果直接复用，渲染不重复请求。

取消实测发现：Promise.all 在一个关联请求失败后会立即拒绝，其余已经发出的请求可能仍在途。修复为保留原错误并等待所有关联请求收尾，再结束准备。这使章节和关联请求均不会越过同步操作的生命周期。

修改版真实沙盒在章节请求开始后取消：只发送首批五个条目的 25 个请求，创建零份文件，返回 cancelled 时实际在途请求为零，随后没有继续请求，manager idle 且无恢复日志。五个预期取消错误由测试捕获，无非预期控制台错误或异常。

新增自动化断言覆盖：

- 每次 HTTP 100ms 时，完整真实 manager 同步丰富模板由串行结构的四轮缩短为三轮（300ms），内容及五次请求数不变。
- 角色接口未返回时，章节和用户状态已能加载。
- 关联资料失败时等待章节收尾，不写入不完整笔记。
- 章节获取失败后不在渲染阶段重复获取。
- 关联接口早失败时等待其他在途接口结束。
