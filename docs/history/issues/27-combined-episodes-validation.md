# Issue #27：合并章节与观看状态请求

## 接口依据与实现

核对 [Bangumi 官方接口定义](https://github.com/bangumi/api/blob/master/open-api/v0.yaml)及[服务端实现](https://github.com/bangumi/server/blob/5fc276a1f22368a80655c2b72427f24d177dee83/web/handler/user/get_episode_collection.go)：章节收藏接口先读取该条目的章节列表，再附加用户状态，因此包含未标记章节及完整章节字段，而非仅返回已收藏章节。

新流程优先用该接口同时提供章节和状态，去掉重复的公开章节请求。每页请求 200 条，按实际返回长度继续分页，直到完整读取；校验字段、可用的 subject_id、偏移、稳定总数和重复 ID。兼容服务器空列表的 null 表示。无认证时直接读取公开章节；认证接口不可用或响应不完整时回退公开章节，使用空状态，不重复探测已失败的认证接口。取消或凭据变化不触发回退。旧独立章节方法保留供其他功能使用。

这同时修复正式同步只读取默认第一页章节的问题。不会跨同步缓存用户状态，不改变文件写入、恢复日志或请求并发预算。

## Production Sandbox 对照

基线为上一轮章节并行优化 aeb759e，两版均使用条目并发五、HTTP 预算二十。测试运行于隔离的真实 Obsidian，使用合成动画数据、本地 HTTP fixture、每请求 100ms 延迟、关闭封面下载。丰富模板含角色、制作公司、章节及关联链接；无预览缓存。两版使用独立输出目录，归一化输出目录后逐份比较完整文件内容，而非只检查文件数量。

完整执行减少约 22.4 秒（12.9%），资料准备减少约 25.7 秒（17.8%），请求减少 1303 次（16.7%）。写入存在约 3.3 秒波动，不把这部分误归因于网络改动。两版的 1303 份输出逐份一致，结束时无在途请求、恢复日志、控制台错误或异常。

该大批量对照各执行一次，且使用本地合成数据，不能视为用户真实账号及网络的 1303 条目复测。它验证了同等内容下减少请求的收益，不证明所有场景都获得相同比例提速；长篇作品完整分页可能比旧版截断读取产生更多请求，但不能为性能牺牲完整性。

## 回归与边界

- 414 项自动化测试（48 个文件）通过，Node 22 npm ci、lint、production build、docs:check、git diff --check 通过。
- 真实 Obsidian 的 235 章节协议测试：合并接口两页得到全部章节和状态；401 或字段缺失后一次回退，公开章节两页完整返回；无认证仅请求公开章节。401 场景产生两条预期错误日志，无未捕获异常。
- 真实批量预加载中取消：首批共 25 个请求，创建零份文件；返回 cancelled 时在途为零，之后没有新请求，manager idle，无待恢复 journal。
- 自动化覆盖未标记与特别篇、服务端缩小分页、空列表、字段缺失、错误 subject_id、重复数据、公开响应截断、无认证、取消及账号变化。
- 固定 100ms 延迟的真实 manager 测试：丰富模板单条目准备只需两轮网络等待（200ms），保留角色、制作公司和已看章节。

当前代码尚未发布，未据此回复或关闭 issue。主要剩余成本仍是其他必需资料请求及文件写入；未引入可能让用户状态过期的跨同步缓存。
